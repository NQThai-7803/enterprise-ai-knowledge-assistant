# Database Design

## 1. Principles

- PostgreSQL is the primary database.
- All schema changes are managed by Alembic migrations.
- Entity primary keys use UUID values generated by the application with `uuid.uuid4`.
- Timestamp columns use timezone-aware PostgreSQL `timestamptz` values and are stored as UTC instants.
- Passwords are never stored in plaintext.
- Raw refresh tokens are never stored in the database.

### refresh_tokens

| Column | Type | Notes |
|---|---|---|
| id | UUID | Primary key, generated by the application |
| user_id | UUID | Required FK to `users.id` |
| token_hash | varchar(64) | Required, unique SHA-256 hex hash of the raw refresh token |
| expires_at | timestamptz | Required |
| revoked_at | timestamptz | Nullable |
| created_at | timestamptz | Required, server default `now()` |

Constraints and indexes:

- `pk_refresh_tokens`
- `uq_refresh_tokens_token_hash`
- `fk_refresh_tokens_user_id_users`
- `ix_refresh_tokens_user_id`
- `ix_refresh_tokens_expires_at`

Foreign key behavior:

```text
refresh_tokens.user_id -> users.id ON DELETE CASCADE
```

Refresh token rules:

- Raw refresh tokens are opaque random values returned only at login or refresh.
- Only `token_hash` is stored.
- `token_hash` is `hashlib.sha256(token.encode("utf-8")).hexdigest()`.
- Refresh rotates tokens: the old row receives `revoked_at`, and a new row is created.
- Token family, IP address, and user agent are not stored in TASK-005.

## 4. Password storage

Only `users.hashed_password` is stored. Plaintext passwords are accepted only by command/runtime input, hashed with `pwdlib` Argon2 helpers, and never persisted in plaintext.

- `DEPARTMENT_DELETED`

### Delete policies

User delete through the API is a soft deactivate: the `users` row remains and `is_active` becomes `false`. Deactivation revokes active refresh tokens.

Department delete through the API is a hard delete. A Department with at least one active User cannot be deleted. If only inactive Users still reference the Department, deletion is allowed and `users.department_id` is set to `NULL` by the foreign key.

### Audit transaction rule

User and Department mutation audit logs are inserted with the same `AsyncSession` and transaction as the business mutation. If audit insertion fails, the business mutation is rolled back. Audit metadata must not contain plaintext passwords, password hashes, access tokens, refresh tokens, token hashes, authorization headers, secret keys, or database URLs.


## 6. TASK-008 document schema

TASK-008 implements the document metadata and explicit permission grant data model only. It does not implement upload, local storage, document APIs, PDF processing, chunks, embeddings, pgvector, or retrieval policies.

### document_status enum

PostgreSQL enum name: `document_status`

Values:

```text
UPLOADED
PROCESSING
READY
FAILED
ARCHIVED
```

`is_deleted` is a separate soft-delete flag and is not represented as a `DocumentStatus` value.

### document_access_scope enum

PostgreSQL enum name: `document_access_scope`

Values:

```text
PRIVATE
DEPARTMENT
ORGANIZATION
```

Scope consistency is protected by database constraint `ck_documents_access_scope_department`:

- `DEPARTMENT` requires `department_id IS NOT NULL`.
- `PRIVATE` and `ORGANIZATION` require `department_id IS NULL`.

### document_permission_level enum

PostgreSQL enum name: `document_permission_level`

Values:

```text
VIEW
EDIT
MANAGE
```

The intended permission order `VIEW < EDIT < MANAGE` is not implemented by string comparison. Explicit mapping belongs to the future document access policy task.

Document delete is intended to be soft delete by setting `is_deleted = true`. `ARCHIVED` is a business status and is distinct from soft delete.

| Column | Type | Notes |
|---|---|---|
| id | UUID | Primary key, generated by the application |
| document_id | UUID | Required FK to `documents.id` |
| user_id | UUID | Nullable FK to `users.id` |
| department_id | UUID | Nullable FK to `departments.id` |
| permission | document_permission_level | Required, defaults to `VIEW` |
| created_by | UUID | Required FK to `users.id` actor |
| created_at | timestamptz | Required, server default `now()` |

Constraints and indexes:

- `pk_document_permissions`
- `ck_document_permissions_exactly_one_grantee`
- `uq_document_permissions_document_user`
- `uq_document_permissions_document_department`
- `ix_document_permissions_document_id`
- `ix_document_permissions_user_id`
- `ix_document_permissions_department_id`
- `ix_document_permissions_created_by`

Foreign key behavior:

```text
document_permissions.document_id -> documents.id ON DELETE CASCADE
document_permissions.user_id -> users.id ON DELETE CASCADE
document_permissions.department_id -> departments.id ON DELETE CASCADE
document_permissions.created_by -> users.id ON DELETE RESTRICT
```

A permission grant must have exactly one grantee: either one User or one Department. Duplicate grants for the same `(document_id, user_id)` or `(document_id, department_id)` are rejected. Permission rows are explicit allow grants only; explicit deny is not supported.

Direct grants supplement access from `access_scope`; they do not reduce access granted by `PRIVATE`, `DEPARTMENT`, or `ORGANIZATION` semantics. Admin implicit access and uploader ownership are not stored as permission rows.
## 7. TASK-010 document access behavior

TASK-010 does not change the database schema and does not add a migration. It implements permission-aware queries over the TASK-008 tables.

Document access rules now implemented in repository/service code:

- List, detail, status, and download apply `documents.is_deleted = false` in PostgreSQL.
- Admin access uses the same soft-delete filter.
- Non-Admin access is an `OR` over Organization scope, same Department scope, uploader ownership, direct User grant, and direct Department grant.
- Direct grant checks use correlated `EXISTS` expressions to avoid duplicate Document rows.
- List `total` counts only accessible Documents after applying the same permission filter and query filters.
- Search is parameterized over `title`, `original_filename`, and `description`.
- Sort fields are allowlisted and include a secondary `documents.id` sort for stable results.

Document deletion remains soft delete by setting `documents.is_deleted = true`. Direct grants remain in `document_permissions` after soft delete, but they do not bypass deleted state.

Department hard delete now checks all Documents referencing `documents.department_id`, including soft-deleted rows, and returns `DEPARTMENT_HAS_DOCUMENTS` before attempting the delete. Direct Department grants still use `ON DELETE CASCADE` and do not block Department deletion.

Permission levels are evaluated through explicit mappings for view, edit, and manage. There is no explicit deny grant.

Before TASK-014, `document_chunks`, pgvector extension, vector columns, vector indexes, embeddings, and RAG retrieval were not implemented. TASK-014 now adds chunk vector storage; permission-aware retrieval and RAG APIs remain future work.

## 8. TASK-014 document_chunks and pgvector schema

TASK-014 adds PostgreSQL pgvector storage for processed chunks.

### document_chunks

| Column | Type | Notes |
|---|---|---|
| id | UUID | Primary key, generated by the application |
| document_id | UUID | Required FK to `documents.id` |
| chunk_index | integer | Required, zero-based per Document |
| text | text | Required original chunk text |
| token_count | integer | Required, greater than 0 |
| character_count | integer | Required, greater than 0 |
| page_numbers | integer[] | Required source pages |
| start_page | integer | Required, greater than 0 |
| end_page | integer | Required, `>= start_page` |
| overlap_token_count | integer | Required, `>= 0` |
| content_sha256 | varchar(64) | Required deterministic SHA-256 of chunk text |
| embedding | vector(384) | Required dense embedding |
| embedding_provider | varchar(64) | Required provider id |
| embedding_model | varchar(255) | Required model name |
| embedding_dimensions | integer | Required, fixed to 384 |
| created_at | timestamptz | Required, server default `now()` |

Constraints and indexes:

- `document_chunks.document_id -> documents.id ON DELETE CASCADE`.
- Unique `(document_id, chunk_index)` via `uq_document_chunks_document_chunk_index`.
- Check constraints protect positive counts, page range, checksum length, non-empty page array, and dimension 384.
- Indexes exist on `document_id`, `(document_id, chunk_index)`, and `content_sha256`.
- HNSW cosine index `ix_document_chunks_embedding_hnsw_cosine` uses `vector_cosine_ops`.

Soft-deleted Documents may still have chunk rows. Future retrieval must join to `documents` and filter `documents.is_deleted = false`, status, and permissions. Permission-aware semantic retrieval is not implemented yet.

Chunk replacement is atomic through repository/service code: new payload is validated before old chunks are deleted, and the repository does not commit. The service owns commit/rollback.

The migration enables `CREATE EXTENSION IF NOT EXISTS vector`. Downgrade drops `document_chunks` and indexes but intentionally does not drop the `vector` extension because it may predate this migration.

## 10. TASK-017 full-text retrieval index

TASK-017 adds one index for keyword retrieval:

```sql
CREATE INDEX ix_document_chunks_text_fts_simple
ON document_chunks
USING gin (
    to_tsvector('simple'::regconfig, text)
);
```

- The index is an expression GIN index; no stored `tsvector` column is added.
- Keyword ranking is computed at query time with `ts_rank_cd(...)` and does not require schema columns.
- The existing `ix_document_chunks_embedding_hnsw_cosine` pgvector HNSW index remains in place for semantic retrieval.
- No search-history table, retrieval-cache table, conversation table, citation table, trigger, `unaccent`, `pg_trgm`, or new extension is introduced.
- The TASK-017 downgrade removes only `ix_document_chunks_text_fts_simple`; it does not drop `document_chunks`, vector columns, the pgvector extension, documents, permissions, or the HNSW vector index.
